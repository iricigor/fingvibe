    Maintain this documentation¶

    The website is built with MkDocs 1.6.1 and Material 9.6.22. Markdown in docs/index.md and docs/manual/ is its single authored source. Images live under docs/screenshots/manual/; the logo is an existing branding asset. One small theme partial keeps the source link static instead of fetching GitHub repository statistics. Fonts and search assets are served locally.

    Existing technical references, archived designs, agent prompts, and backlog contracts remain in the repository. They are deliberately not website chapters. Links to them open their GitHub source.

    Build locally¶

    Use Python 3.12 and run these commands from the repository root. A virtual environment keeps documentation dependencies separate:

    python -m venv .venv-docs
.\.venv-docs\Scripts\python.exe -m pip install -r tools\requirements-docs.txt
.\.venv-docs\Scripts\python.exe tests\Documentation.Tests.py
.\.venv-docs\Scripts\python.exe tests\DocumentationPublish.Tests.py
.\.venv-docs\Scripts\python.exe -m mkdocs build --strict
.\.venv-docs\Scripts\python.exe tools\Check-Documentation.py site

    The generated output is site/, which is ignored by Git. Do not commit it. For a local preview:

    .\.venv-docs\Scripts\python.exe -m mkdocs serve

    Open the local URL printed by MkDocs. Stop the server when finished. The website is separate from the native WinUI application.

    Publishing¶

    The Documentation workflow builds changed documentation on pull requests. It checks links, fragments, assets, image alternative text, decorative icon accessibility, and search output before uploading a Pages artifact. Pull requests and feature-branch manual runs do not deploy. Publisher regression tests verify archive preservation, bounded file ownership, stale-file cleanup, unsafe-path rejection, and repeat publication.

    After a matching push to main, the deployment job publishes the checked artifact to GitHub Pages. A manual workflow run on main can republish it without changing app releases. The main-only publication job has narrowly scoped contents/Pages write permissions so it can update the existing publishing branch and request a build.

    The repository already publishes native PR screenshots under ui-review/ on the gh-pages branch. Documentation shares that branch without replacing this archive. A manifest tracks only documentation-owned files so obsolete manual files can be removed without deleting screenshots or unrelated content. Concurrent branch updates are rebased before a bounded push retry.

    Keep Settings > Pages > Source: Deploy from a branch, using gh-pages and its root folder. The github-pages environment must allow main for the publishing job; its existing gh-pages allowance is preserved. The job explicitly requests a Pages build after publication, rather than relying on a token-generated push to trigger another workflow. Existing screenshot publishing remains unchanged. These settings do not change application release policy or branch protection.

    A successful PR build is not proof that the live site was deployed. After publication, the main job waits for the Pages build and verifies the live revision marker, manual homepage, local search data, and all thirteen new images. After merge, check that result and the real /fingvibe/ project URL. Inspect interactive search and navigation there too.

    Writing rules¶

    Use short sentences and familiar words for non-native speakers. Explain a technical term when it first appears. Use exact UI labels and one action per numbered step. Describe the expected result and keep warnings beside risky actions.

    Keep detailed implementation/test internals in contributor or technical records. Avoid idioms, decorative jargon, and claims of continuous presence. When behavior changes, update related pages together and update the homepage's release baseline after verification.

    Images and icons¶

    Reuse meaningful app imagery where possible. Keep text beside icons and provide descriptive alternative text for screenshots. Decorative SVGs should be hidden from assistive technology, not announced repeatedly.

    Use privacy-safe native screenshots, never an unredacted real inventory. Record source revision, run, test identity, dimensions, edits, and visible state in Screenshot sources. Do not imply that a ready-state capture shows real measured results.

    Do not obtain fresh screenshots by automating a working user's desktop. Use existing disposable Windows CI capture tooling.
